Assignment #3: Data and Query Design

Learning Assistant — Team 08

Platform Development Course · Digital Campus Platform · Track 2 (Advanced Edge)
Stack: Cloudflare Workers · Hono · TypeScript · Cloudflare D1

1. Introduction

Learning Assistant is a course question-answering service built as part of a larger university Digital Campus Platform. It lets a student ask a course-scoped question and receive an answer that is grounded only in materials an instructor or teaching assistant has explicitly approved for that course.

Two properties define the product:

  • Every substantive answer carries citations. An answer is either backed by one or more approved knowledge sources (with excerpts a student can verify), or the system honestly reports that it found nothing and points the student to their instructor — it never invents an answer.
  • It is one service among many. In the Digital Campus Platform, each team owns one focused service with its own data boundary, integrating with the rest of the platform through REST APIs and versioned webhook events rather than shared databases.

This assignment covers the data and query design for that service: the relational schema, why the chosen database fits, and the REST API that reads and writes it.

2. Database Choice

Cloudflare D1 (a managed, serverless SQLite database) was chosen for Learning Assistant.

ReasonWhy it matters here
SQLite-compatible relational databaseThe domain is inherently relational: a course has sources; a question has (at most) one answer; an answer has citations and feedback. Foreign keys and UNIQUE/CHECK constraints express these rules directly in the schema.
Native Cloudflare Worker integrationThe API is a Hono app on Cloudflare Workers. D1 is bound directly into the Worker (env.learning_assistant_db) with no separate network hop or driver.
Simple migrations, local and remotewrangler d1 migrations apply ... --local / --remote runs the same numbered SQL migration against a local simulated database or the real remote one.
Parameterized SQL, indexes, FKs, CHECK constraintsStandard SQLite: prepared statements with bound parameters, indexes, foreign keys with ON DELETE behavior, column-level CHECK constraints — everything this schema needed.
Cost / operational simplicity for a student MVPWorkable free tier, no server to provision or patch, scales to zero between requests — appropriate for a course project.

A realistic limitation: D1 is suitable for this relational MVP, but it does not provide native vector search for future semantic retrieval — that would need an additional component if added later.

3. Data Ownership and Boundaries

  • Learning Assistant owns its own D1 database and schema exclusively. No other Digital Campus Platform service reads or writes these tables directly, and this service does not reach into any other service's data store either.
  • course_id, student_id, user_id, and created_by are external identifiers supplied by other platform services (Course Catalog, Student Identity), stored here only as opaque references.
  • Cross-service integration happens through REST APIs and signed webhook events, never direct database access across service boundaries.
  • received_events exists to support this: an idempotency ledger for future inbound webhook processing (e.g. assignment.published). Its primary key is the event id, so redelivery is safe to detect and skip.

5. Relational Schema

The full, authoritative schema lives in migrations/0001_initial_learning_assistant_schema.sql.

knowledge_sources

Instructor/TA-approved learning material for one course — the only thing the fallback search is ever allowed to draw an answer from.

7. API and CRUD Design

MethodPathRolePurpose
GET/v1/healthnoneLiveness check
POST/v1/sourcesinstructorCreate a knowledge source
PATCH/v1/sources/{id}instructorUpdate a knowledge source
DELETE/v1/sources/{id}instructorArchive (soft delete) a knowledge source
GET/v1/courses/{courseId}/sourcesstudent, instructorList a course's approved sources
POST/v1/questionsstudentAsk a question; get a fallback answer + citations
GET/v1/questions/{id}owning student, instructorRead a question with its answer and citations
POST/v1/answers/feedbackstudent, instructorRate an answer (1–5)

CRUD mapped onto the sources resource

OperationEndpointNotes
CreatePOST /v1/sourcesInstructor only; created_by from identity header, never the body
ReadGET /v1/courses/{courseId}/sourcesReturns only status = approved sources for that course
UpdatePATCH /v1/sources/{id}Instructor only; updates only supplied fields plus updated_at
Archive (in place of hard Delete)DELETE /v1/sources/{id}Instructor only; see below

DELETE is intentionally a soft archive, not a hard delete: the row is never physically removed; status becomes archived and updated_at refreshes; the source immediately disappears from future listings; any citation already pointing at it is preserved; the operation is idempotent.

9. Data Quality, Security, and Integrity

  • Request validation. Dependency-free helpers reject malformed JSON, non-object bodies, empty required strings, and wrong types before any database access (400 VALIDATION_ERROR).
  • Temporary role-based authorization. x-user-id / x-user-role middleware rejects missing/invalid identity (401) and a route-level role guard rejects a disallowed role (403).
  • Student question ownership. A student can only read their own question; an instructor can read any question in a course — enforced server-side.
  • Instructor-only source management. Create/update/archive of knowledge sources is restricted to the instructor role.
  • Parameterized SQL only. All queries use D1's bound-parameter API; dynamic PATCH updates build from a fixed column whitelist, never arbitrary client keys.
  • Foreign keys and CHECK constraints. Relationships and finite value sets are enforced by the database itself — verified directly (§10).
  • Correlation IDs. Every response carries x-correlation-id; every error body includes the same value.
  • Archived-source behavior. Excluded from future retrieval; existing citations remain intact.
  • Approved-source-only fallback retrieval. Only status = approved sources in the question's own course are ever searched or cited.
  • No source means no invented answer. A fixed, honest message is returned instead of a guess.

10. Testing and Verification

  • Type check: npm run typecheck → pass, no errors.
  • Automated tests: npm test → 47 / 47 passing across 6 test files.
  • Local migration: applied cleanly to a fresh local D1 — 15 statements, all six tables and eight indexes present; both column defaults confirmed by insert-then-read verification.
  • Local API smoke test: all seven business endpoints plus health exercised end-to-end against a real local D1 database — source CRUD/archive/idempotency, draft exclusion, matching and non-matching question flows, question-ownership authorization, and feedback creation.
  • Known limitation — plain Node Vitest vs. live D1: the automated suite runs in a plain Node environment (no @cloudflare/vitest-pool-workers), so database-backed success paths are verified manually (above) rather than by an automated integration test. The 47 automated tests cover pure logic and every route's pre-database-access path.
  • Known limitation — simple keyword matching: the fallback matcher does case-insensitive substring matching on tokens of length ≥ 2, so a very common short token can occasionally match incidentally against unrelated text containing that substring. This is a known characteristic of the current simple-by-design matching approach.
  • Remote migration and schema verification: performed, with explicit team approval. wrangler d1 migrations apply learning-assistant-db --remote reported the migration was already applied (no changes made); a direct sqlite_master query against the remote database confirmed all 6 tables and 8 indexes are present and match the local schema. Full evidence in docs/assignment-3-evidence/remote-migration-verification.txt.
  • Remote API testing: not performed. The Worker itself has not been deployed (wrangler deploy) or exercised against the remote database — only the schema was verified remotely.

11. Conclusion

The Learning Assistant schema — six tables, eight indexes, foreign keys, and CHECK constraints in a single migration file — directly supports the product's core promise: an answer is either grounded in a specific, approved, citable source, or the system says so honestly. Cloudflare D1 was a good fit because the domain is small and relational, the Worker binding requires no extra infrastructure, and migrations are simple to apply both locally and remotely. The seven /v1 REST endpoints provide full CRUD (create/read/update/archive) over knowledge sources, plus the question → fallback-answer → citation → feedback flow, all demonstrated above against a real local database with representative fictional data. Remote deployment is designed and ready but intentionally gated behind explicit team approval, consistent with treating a production database migration as a deliberate, reviewed action.
